Despliegue e Integración GitOps

Kubernetes (Minikube) + GitHub + ArgoCD en entorno Ubuntu WSL2

1. Preparación del Entorno Local (Pre-work)

Se configuró un entorno local aislado sobre Ubuntu WSL2, verificando los componentes principales:

  • Docker Desktop: Motor de contenedores habilitado con integración WSL2.
  • Minikube (v1.39.0): Clúster mononodo inicializado sobre Docker asignando recursos optimizados: 
    minikube start --driver=docker --cpus=4 --memory=4096 --force
  • Kubectl & ArgoCD CLI: Clientes de línea de comandos para la gestión de recursos de Kubernetes y la sincronización declarativa de GitOps.

2. Arquitectura de Integración GitOps (GitHub + ArgoCD + Kubernetes)

El modelo GitOps adopta a Git como la fuente única de verdad (Single Source of Truth). La sincronización se ejecuta mediante un patrón de extracción activa (Pull Model):

1. GitHub

Almacena manifiestos YAML declarativos en la rama dev (carpeta manifests/).

→

2. ArgoCD Controller

Vigila continuamente los cambios en Git y los compara con el estado real del clúster.

→

3. Clúster Minikube

Aplica los recursos en el namespace objetivo (challenge-gitops).

Comandos ejecutados para la integración de ArgoCD:

  1. Instalación del plano de control de ArgoCD: 
    kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
  2. Exposición e inicio de sesión en ArgoCD: 
    kubectl port-forward svc/argocd-server -n argocd 8080:443 &
argocd login localhost:8080 --username admin --insecure
  3. Creación de la aplicación vinculando GitHub y Kubernetes: 
    argocd app create hello-gitops \
  --repo https://github.com/IberthAlexander/challenge-argo-k8s.git \
  --revision dev \
  --path manifests \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace challenge-gitops
  4. Sincronización declarativa forzada: 
    argocd app sync hello-gitops --force

3. Conceptos Clave de Kubernetes

  • Pod: Unidad mínima de cómputo en Kubernetes que agrupa uno o más contenedores compartiendo red y almacenamiento.
  • Deployment: Objeto declarativo que controla el ciclo de vida, las réplicas y las actualizaciones progresivas de los Pods.
  • Service: Abstracción de red que provee un punto de acceso estable (IP y Puerto) hacia un conjunto de Pods seleccionados por sus etiquetas.

Estructura del Manifiesto Unificado Base (deployment.yaml)

A continuación se presenta el manifiesto declarativo unificado subido al repositorio central de GitHub en la ruta manifests/deployment.yaml dentro de la rama dev:

apiVersion: v1
kind: Namespace
metadata:
  name: challenge-gitops
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-deployment
  namespace: challenge-gitops
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello-web
  template:
    metadata:
      labels:
        app: hello-web
    spec:
      containers:
      - name: web
        image: hashicorp/http-echo:latest
        args:
          - "-text=Hola desde ArgoCD y Kubernetes local!"
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
            cpu: "200m"
        ports:
        - containerPort: 5678
---
apiVersion: v1
kind: Service
metadata:
  name: hello-service
  namespace: challenge-gitops
spec:
  type: NodePort
  selector:
    app: hello-web
  ports:
    - port: 80
      targetPort: 5678
      nodePort: 30081

Buenas Prácticas Incluidas

El manifiesto incluye límites de recursos (requests y limits) para prevenir el agotamiento de memoria del nodo, configuración de replicas en 2 para alta disponibilidad básica y exposición de servicio NodePort para pruebas en entorno local.

Troubleshooting GitOps: Resolución de 5 Situaciones de Error

Metodología de diagnóstico avanzado y resolución declarativa sin aplicar parches manuales directo en el clúster (cero uso de kubectl edit directo).

Caso 1: Solicitud de Memoria Superior a la Disponible (`Insufficient memory`)

Escenario: El manifiesto exige memory: "8Gi" por Pod (16 GB total para 2 réplicas), superando la memoria libre del nodo de Minikube (7.46 GB disponibles según kubectl describe node minikube).

1. Comandos de Validación:

kubectl get pods -n challenge-gitops
kubectl describe node minikube | grep -A 8 "Allocatable"

2. Obtención de Evidencia / Logs del Evento (`kubectl describe`):

kubectl describe pod -l app=hello-web -n challenge-gitops

Salida obtenida en la sección de eventos del Scheduler:

Warning  FailedScheduling  default-scheduler  0/1 nodes are available: 1 Insufficient memory. preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.

3. Resolución bajo Flujo GitOps:

  1. Editar manifests/deployment.yaml en GitHub actualizando los recursos a un valor válido (128Mi).
  2. Realizar git commit y git push origin dev.
  3. Sincronizar el clúster con la CLI de ArgoCD: 
    argocd app sync hello-gitops --force

Caso 2: Imagen de Contenedor Errónea o Inexistente (`ImagePullBackOff` / `ErrImagePull`)

Escenario: Se introdujo intencionadamente una imagen inexistente con typo en el manifiesto YAML (hashicorp/http-echo-rotte:v99) para evaluar el comportamiento del controlador Kubelet y el estado de sincronización en ArgoCD.

1. Comandos de Validación:

kubectl get pods -n challenge-gitops
argocd app get hello-gitops

Resultado: El Pod se queda en estado Waiting mostrando la razón ErrImagePull y pasa al bucle ImagePullBackOff. En ArgoCD, la aplicación reporta un estado de salud Degraded.

2. Obtención de Evidencia / Logs del Evento (`kubectl describe pod`):

kubectl describe pod hello-deployment-85f5898499-rpvmk -n challenge-gitops

Salida exacta de los eventos capturados en el clúster:

Containers:
  web:
    Image:      hashicorp/http-echo-rotte:v99
    State:      Waiting
      Reason:   ErrImagePull
    Ready:      False
Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Normal   Scheduled  40s                default-scheduler  Successfully assigned challenge-gitops/hello-deployment-85f5898499-rpvmk to minikube
  Normal   Pulling    24s (x2 over 40s)  kubelet            spec.containers{web}: Pulling image "hashicorp/http-echo-rotte:v99"
  Warning  Failed     23s (x2 over 39s)  kubelet            spec.containers{web}: Failed to pull image "hashicorp/http-echo-rotte:v99": failed to pull and unpack image "docker.io/hashicorp/http-echo-rotte:v99": failed to resolve reference "docker.io/hashicorp/http-echo-rotte:v99": pull access denied, repository does not exist or may require authorization
  Warning  Failed     23s (x2 over 39s)  kubelet            spec.containers{web}: Error: ErrImagePull
  Normal   BackOff    8s (x2 over 38s)   kubelet            spec.containers{web}: Back-off pulling image "hashicorp/http-echo-rotte:v99"
  Warning  Failed     8s (x2 over 38s)   kubelet            spec.containers{web}: Error: ImagePullBackOff

3. Resolución Paso a Paso bajo Flujo GitOps:

  1. Editar el archivo manifests/deployment.yaml en GitHub corrigiendo la imagen a su tag oficial funcional: 
    spec:
  containers:
  - name: web
    image: hashicorp/http-echo:latest
  2. Enviar los cambios al repositorio central en GitHub: 
    git add manifests/deployment.yaml
git commit -m "fix: corregir imagen erronea a hashicorp/http-echo:latest"
git push origin dev
  3. Ejecutar la sincronización forzada a través de la CLI de ArgoCD: 
    argocd app sync hello-gitops --force

Caso 3: Requerimiento de Hardware Inexistente / GPU (`Unsatisfiable nodeSelector`)

Escenario: El manifiesto solicita un nodo específico equipado con GPU (nodeSelector: accelerator: nvidia-tesla-v100), pero el clúster local Minikube únicamente posee nodos CPU genéricos.

1. Comandos de Validación:

kubectl get pods -n challenge-gitops
kubectl get nodes --show-labels

2. Obtención de Evidencia / Logs del Evento (`kubectl describe`):

kubectl describe pod hello-deployment-8645d54c8d-hw2n7 -n challenge-gitops

Salida obtenida en los eventos del Scheduler:

Node-Selectors:              accelerator=nvidia-tesla-v100
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  58s   default-scheduler  0/1 nodes are available: 1 node(s) didn't match Pod's node affinity/selector. preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.

3. Resolución bajo Flujo GitOps:

  1. Remover la sección nodeSelector restrictiva del manifiesto en GitHub.
  2. Subir los cambios con git push origin dev.
  3. Reaplicar el estado deseado con argocd app sync hello-gitops --force.

Caso 4: Falla de Liveness Probe / Health Check (`CrashLoopBackOff`)

Escenario: Se configuró una sonda de salud (`livenessProbe`) apuntando a un puerto o ruta HTTP inexistente (path: /healthz), provocando que Kubelet mate y reinicie continuamente el contenedor.

1. Comandos de Validación y Diagnóstico Avanzado:

kubectl get pods -n challenge-gitops -w
kubectl logs -l app=hello-web -n challenge-gitops --previous
kubectl describe pod -l app=hello-web -n challenge-gitops

2. Obtención de Evidencia en Eventos del Kubelet:

Warning  Unhealthy  kubelet  Liveness probe failed: HTTP probe failed with statuscode: 404
Normal   Killing    kubelet  Container web failed liveness probe, will be restarted

3. Resolución bajo Flujo GitOps:

  1. Ajustar el path del probe a la ruta raíz / funcional en GitHub o remover el bloque defectuoso.
  2. Subir cambios con git push origin dev y sincronizar con argocd app sync hello-gitops --force.

Caso 5: Desalineación de Puertos de Red (`targetPort` Incorrecto en Service)

Escenario: Los Pods figuran sanos en Running (1/1), pero el `Service` mapea el targetPort al puerto 9999 en lugar del puerto 5678 donde escucha el contenedor.

1. Comandos de Validación de Red y EndpointSlices:

kubectl get svc hello-service -n challenge-gitops
kubectl get endpoints hello-service -n challenge-gitops
kubectl get endpointslices -n challenge-gitops

Salida obtenida en los Endpoints del clúster:

NAME           ENDPOINTS                           AGE
hello-service   10.244.0.23:9999,10.244.0.24:9999   58s

2. Prueba de Conectividad con Pod Efímero de `curl`:

kubectl run curl-test --image=curlimages/curl -it --rm -n challenge-gitops -- sh
~ $ curl -v http://hello-service.challenge-gitops.svc.cluster.local

Respuesta HTTP comprobada tras corregir el `targetPort` a 5678:

< HTTP/1.1 200 OK
< X-App-Name: http-echo
< Content-Type: text/plain; charset=utf-8
Hola desde ArgoCD y Kubernetes local!

3. Resolución bajo Flujo GitOps:

  1. Editar `manifests/deployment.yaml` corrigiendo targetPort: 5678 en GitHub.
  2. Realizar git push origin dev y forzar sincronización en ArgoCD (argocd app sync hello-gitops --force).

Resumen de Reglas de Diagnóstico Rápido

Error de Indentación (YAML)

Causa: Clave containers: mal alineada.

Diagnóstico: Deployment.apps is invalid: spec.template.spec.containers: Required value.

Requests > Limits

Conflicto: requests: 512Mi vs limits: 256Mi.

Resultado: Rechazo de API de Kubernetes o reinicios por OOMKilled.

Workflow GitOps

Ciclo: 1. Detectar (get pods/svc) → 2. Evidencia (describe/endpoints/curl) → 3. Fix en Git → 4. Sync ArgoCD.

Conclusión de Buenas Prácticas GitOps

Ningún fallo en el clúster debe corregirse ejecutando parches manuales (kubectl edit / kubectl set). Toda modificación requiere ser comiteada en GitHub para mantener la audibilidad, la trazabilidad y la convergencia automática que ofrece ArgoCD.
